# ТЗ: MariaDB, избранное и вход через Telegram

**Цель:** пользователь входит через Telegram и получает свои любимые треки и альбомы на любом устройстве. Авторизация и избранное реализуются и принимаются одним этапом.

## 1. Объём работ

- Расширить существующий FastAPI backend и интерфейс в `dist/`.
- Добавить вход через Telegram, профиль с именем пользователя и выход.
- Перенести избранное авторизованных пользователей в MariaDB: добавление, удаление, списки «Любимые треки» и «Любимые альбомы», новые сверху.
- Поддержать демотреки, треки из поиска YouTube и существующие альбомы приложения. Поиск внешних альбомов, плейлисты в БД и хранение аудиофайлов в этот этап не входят.
- Лайк альбома независим от лайков его треков. Кнопки должны явно различать эти действия.

## 2. Вход и сессия

- Использовать [Telegram Login через OpenID Connect](https://core.telegram.org/bots/telegram-login): Authorization Code Flow с PKCE, scopes `openid profile`. Настроить бота, Client ID/Secret и разрешённый callback URL через BotFather.
- Backend проверяет одноразовый `state`, подпись ID token, `iss`, `aud`, `exp`; повторный callback отклоняется. Идентификатор аккаунта — проверенная пара `iss` + `sub`, а не username.
- После входа создать серверную сессию на 30 дней. В cookie хранить случайный токен, в БД — его хеш и срок действия. Cookie: `HttpOnly`, `SameSite=Lax`, в production — `Secure`; выход отзывает сессию.
- В production frontend и `/api` обслуживать с одного HTTPS origin. Изменяющие запросы защитить от CSRF; для локального запуска разрешить только явно заданные origins с credentials.
- Гость может искать и слушать музыку; попытка поставить лайк предлагает войти. Без сессии API избранного возвращает `401`. После выхода очистить пользовательское избранное из памяти интерфейса.

## 3. Данные и API

Минимальные таблицы MariaDB:

| Таблица | Данные и ограничения |
| --- | --- |
| `users` | Внутренний ID, уникальные `telegram_issuer` + `telegram_subject`, имя, username и аватар при наличии, дата создания. |
| `sessions` | Хеш токена, FK пользователя, срок действия. |
| `likes` | FK пользователя, тип `track/album`, источник, стабильный ID объекта, название, исполнитель, обложка, длительность при наличии, дата добавления. Уникальность `(user_id, type, source, source_id)`. |

- Для YouTube использовать `video_id`; демотрекам и альбомам назначить постоянные ключи, независимые от позиции в массиве. ID сравнивать с учётом регистра. Метаданные нужны для показа избранного после перезапуска; временные аудиоссылки не сохранять, при Play повторно вызывать существующий resolver.
- Все запросы ограничивать пользователем из серверной сессии; `user_id` от клиента не принимать. Валидировать типы, источники, ID и размеры полей. Добавить FK и индекс для выборки избранного пользователя по типу и дате.
- API под `/api/v1`: `GET /auth/telegram/start`, `GET /auth/telegram/callback`, `GET /auth/me`, `POST /auth/logout`; `GET /likes?type=track|album&limit=50&offset=0` (максимум 100); `PUT /likes/{type}/{source}/{source_id}` с метаданными и `DELETE` по тому же пути. Список возвращает `items` и `has_more`, порядок — дата и ID по убыванию.
- Повторные PUT/DELETE безопасны и не создают дублей, включая параллельные запросы. Повторный PUT не меняет дату добавления. При ошибке сохранения UI восстанавливает прежнее состояние и показывает ошибку рядом с действием.
- Старые лайки из `openmusic-likes` предложить импортировать после входа по явному согласию. Переносить только распознанные демотреки, объединять без дублей; очищать старый ключ только после полного успеха. Плейлисты оставить в localStorage.

## 4. Поставка

- Добавить миграции схемы, Compose-сервис MariaDB с постоянным volume и healthcheck, `.env.example` без секретов. Закрепить версию образа и зависимости; подключение к БД и Telegram настраивать через окружение.
- Обновить README: запуск БД и backend, применение миграций, настройка Telegram и HTTPS, создание и восстановление резервной копии. Секреты не передавать во frontend и не записывать в логи.
- При недоступности БД API авторизации/избранного возвращает контролируемую ошибку `503`; UI не сообщает об успешном сохранении. Поиск и воспроизведение сохраняют работоспособность.

## 5. Единая приёмка

Этап принят только при выполнении всех пунктов:

1. На чистой БД применяются миграции; реальный вход через Telegram создаёт пользователя, повторный вход открывает тот же аккаунт. Поддельный/просроченный токен, неверный `state` и повторный callback отклоняются.
2. Пользователь добавляет и удаляет демотрек, найденный YouTube-трек и альбом. Лайк альбома не меняет лайки треков; повторные и параллельные запросы не создают дублей.
3. После обновления страницы, перезапуска backend/БД и входа на другом устройстве избранное сохраняется. Сохранённый YouTube-трек запускается через resolver без повторного поиска.
4. Два Telegram-аккаунта видят только свои лайки. Гость, истёкшая и отозванная сессии не получают доступ; после выхода данные прошлого пользователя не видны.
5. Импорт старых лайков требует согласия, не создаёт дублей и не теряет исходные данные при ошибке. Сбой БД/сети отображается без ложного лайка.
6. Автотесты авторизации, изоляции пользователей и операций с лайками проходят на тестовой MariaDB; существующие тесты backend и плеера проходят. Реальный Telegram-вход и сценарий с двумя устройствами проверены вручную, результаты записаны в PR.

Для сквозной приёмки нужны настроенное Telegram-приложение, тестовые аккаунты и доступный HTTPS callback. Моки не заменяют проверку реального входа.
